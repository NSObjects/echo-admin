# Architecture Smell Report

**Project:** echo-admin
**Scope:** 全项目（internal/ + cmd/，137 个 Go 文件，非测试代码约 20,833 行，测试代码约 10,822 行）
**Date:** 2026-08-28
**Analyzer:** smell skill (Ducc)

---

## Executive Summary

echo-admin 是一个纪律良好的 **module-first 模块化单体**：8 个业务模块（access/auth/identity/settings/apitoken/audit/fileasset/setup）全部遵循 `domain / usecase / adapters / http` 标准结构，**模块间零直接 import、零反向依赖 boot、domain 层零 Echo/GORM/platform 泄漏**——这三条架构红线全部干净，boot 桥接普遍只做类型映射且注释声明规则归属。命名高度一致（无 Manager/Helper/Util 类泛化命名）、无 goroutine 泄漏风险、无 SQL 注入、无深嵌套箭头反模式。作为模板项目，其边界纪律在同类项目中属上游水平。

但模块**内部**存在明显退化，集中在三类根因：**(1) 聚合失控**——settings usecase 把 4 个不相关配置域（configs/params/dictionaries/versions）挤进 1 个 struct + 24 方法 Store 接口，auth usecase 持有 8 个依赖、7 种职责；**(2) 跨模块样板复制家族**——审计记录函数逐字复制 5 份（且硬编码 `Success: true`，失败操作永不入审计）、分页样板复制 6 份、域错误映射表复制 7 份；**(3) 幽灵基础设施**——Redis 和 MongoDB 全链路接线（配置/资源/DI/健康检查）却零消费者，apperr 甚至有 `WrapKafka` 而项目根本没有 Kafka。

最严重的单项问题是**版本/菜单/字典导入操作无事务原子性**：`ImportVersion` 三阶段各自独立执行，中途失败会留下半套菜单和半套字典，破坏权限数据一致性。测试方面最大的缺口是 **3,525 行 MySQL adapter 代码零测试覆盖**（项目刻意不用 DB 测试设施），audit 模块整个后端只有 1 个测试文件且从不验证响应体。

**Critical: 1 | Warning: 8 | Suggestion: 5 | Candidate（需测量）: 4**

## Architectural Style Detected

**Modular Monolith（module-first）+ Composition Root（internal/boot）+ 消费方定义端口（usecase-owned store interface）**，接近 Hexagonal 的端口适配器思想但无显式 ports 命名。

### Style Expectations vs. Reality

| 期望 | 现实 | 状态 |
|------|------|------|
| 模块间不直接 import，依赖经 boot 桥接 | 全量扫描零违规；6 类桥接集中在 business.go | ✅ |
| domain 不依赖 transport/DB/SDK/platform | 全量 grep 零命中 | ✅ |
| modules 不反向依赖 boot | 零违规 | ✅ |
| platform 不 import 业务模块 | 零违规 | ✅ |
| usecase 拥有 store 接口（接口定义在使用方） | 8/8 模块遵守；但 auth 的 `New()` 用 7 个位置参数传依赖，同一 store 填 3 个接口槽 | ⚠️ |
| handler 只做解析/校验/转换/调用/响应 | fileasset 的上传补偿删除、删除顺序规则写在 handler | ⚠️ |
| HTTP adapter 有行为测试 | 各模块 handler_test 存在，但 audit 的测试只数调用不验响应体 | ⚠️ |
| 默认开发路径有 `adapters/memory`（AGENTS.md 承诺） | 8/8 模块只有 `adapters/mysql`，文档与事实不符 | 🔴 |
| 只保留必要基础设施 | Redis/MongoDB 全链路接线、零消费者 | 🔴 |

## Findings by Category

### 🔴 Critical Issues (Must Fix)

1. **导入操作无事务原子性** —— 版本导入（菜单 + 字典 + 版本记录）三阶段无外层事务，字典导入逐条独立事务，菜单导入逐节点 6-10 条 SQL 无事务；中途失败留下半态权限数据。

### 🟡 Warnings (Should Fix)

1. **幽灵基础设施：Redis/MongoDB 全链路零消费者**，apperr 含 `WrapKafka` 引用不存在的 Kafka；限流注释声称 "across app instances" 实际由 MySQL 表实现。
2. **settings usecase 聚合 4 个不相关配置域**（29 导出方法 / 24 方法 Store 接口）。
3. **auth usecase 8 依赖 7 职责**，`UpdateProfile` 与 identity 形成双写入口并绕过其角色委托校验路径。
4. **`RoleIsSuper` 桥接把角色压成裸 bool**，三个调用点各自重复查库——直接违反 AGENTS.md「不要把重要状态压成裸 bool」明文。
5. **`recordOperation` 逐字复制 5 份 + `Success: true` 硬编码**，失败操作永不入审计（审计完整性缺陷与 DRY 双重问题）。
6. **跨模块样板复制家族**：分页样板 ×6、域错误映射表 ×7、Role/Menu DTO 双份映射、集合工具 ×4、MySQL 1062 判定 ×5、`currentAdminID` ×3。
7. **MySQL adapter 3,525 行零测试**；audit 模块 usecase/domain/store 全无测试；audit handler 测试只数调用次数、从不验证响应体。
8. **数据访问模式不一致**：roles/apis/admins/params 四类列表全表加载+内存分页，而 audit/apitoken/fileasset 正确下推 SQL；`roleScope` 被 12 个入口调用且每次全表加载 roles，identity.Update 单请求重复加载 3 次。

### 🔵 Suggestions (Nice to Fix)

1. apperr/requestctx 死导出代码（`WrapKafka`/`WrapRedis`/`WrapExternal`/`NewTokenInvalid` 等 11 个零调用导出）。
2. fileasset handler 持有上传编排与补偿删除（有注释声明系有意设计，但一致性策略仍是业务规则）。
3. settings usecase 内做 `json.MarshalIndent` 下载序列化（表现层关注点下沉）。
4. O(n²) 冷路径合集（exportMenuTree 递归全量扫描、findMenuByPath 线性查找、ensureRolesMutable 线性 findRole 等；同文件已有正确建 map 的先例）。
5. 杂项：AGENTS.md `adapters/memory` 承诺失真；auth store `truncate` 按 byte 切割可能截断 UTF-8；下载接口 `Content-Disposition` 文件名未过滤 version 字符串。

### Candidates Requiring Measurement

不计入 severity 总数，见文末详细定义。

1. 每受管请求约 5-6 次 DB 往返（installation_state 每请求查询无缓存 + session/admin + AuthorizeRoute 3 查询）。
2. GORM `Count` 后复用同一条链继续 `Find`（audit/fileasset），零测试保护。
3. `login_sessions` / `auth_login_attempts` 表只增不减（无清理任务，靠惰性状态判断）。
4. `casbinSnapshot` 循环内逐角色查库（/me、Login 路径；代码注释已声明不在每请求路径）。

## Detailed Findings

### Finding #1: 导入操作无事务原子性，失败留下半态权限数据

- **Category:** Architecture（数据一致性）
- **Severity:** 🔴 Critical
- **Anti-Pattern:** 缺失事务边界（原子性违背）
- **Location:** `internal/modules/settings/usecase/usecase.go:492-513`（ImportVersion）、`internal/modules/settings/usecase/usecase.go:680-690`（importVersionDictionaries 循环）、`internal/modules/access/usecase/usecase.go:418-478`（ImportMenuTree/importMenuTree）
- **Confidence:** High
- **Evidence strength:** Observed（代码路径确认，失败场景为推断但路径确定）
- **Failure or change scenario:** 管理员导入版本包，菜单导入成功后字典导入第 3 条因唯一键冲突失败：菜单已是新树、字典是半新半旧、版本记录未创建。下次重导时 `ImportMenuTree` 面对的 existing 集合与首次不同，可能产生重复或丢失；菜单与路由暴露表（route exposure）不一致直接影响授权判断。
- **Primary principle:** Fail Fast / 数据一致性
- **Description:** `ImportVersion` 串联三阶段——`importVersionCatalog`（access 菜单导入，自身无事务）、`importVersionDictionaries`（每个 dictionary 一次独立事务的 Delete+Create，外层无事务）、`CreateVersion`——之间没有外层事务。`importMenuTree` 递归内每个节点调 `UpdateMenu`/`CreateMenu`，每节点产生 6-10 条 SQL（Find + Save + 按钮全量替换 + loadMenu 重载）且不在事务中。字典循环中每条 `DeleteDictionary`（自带事务，3 条 SQL）+ `CreateDictionary`（INSERT + Preload 回读）。对照：setup 模块的安装流程（setup/usecase/usecase.go:42-67）正确地全程包在单事务里，证明项目具备该能力但导入路径没有用。
- **Evidence:** `importVersionDictionaries` 循环体逐字典 Delete+Create；`importMenuTree` 逐节点调用会触发完整 UpdateMenu 生命周期；`setupTransactionRunner`（boot/business.go:558-623）已提供事务端口但仅用于 setup。
- **Measured/observed impact:** 冷路径（管理操作），但一旦触发即产生需要人工修复的权限数据半态；菜单/按钮授权是 access 域核心数据。
- **Recommendation:** 让导入路径复用 `setupTransactionRunner` 同款事务端口：在 boot 为 access/settings 的导入操作提供事务包裹，store 的导入方法接受事务性 `*gorm.DB`（现有 `WithDB` 已支持）。字典导入改为「先全量删后全量建」于同一事务内。
- **Verification:** 行为测试：注入一个在字典导入第 N 条必然失败的 fake store，断言事务回滚后菜单与字典均保持导入前状态（setup usecase_test 已有同型测试可参考，usecase_test.go:137-171 的 `runner.tx.completed` 模式）。

### Finding #2: 幽灵基础设施——Redis/MongoDB 全链路接线、零消费者

- **Category:** Architecture
- **Severity:** 🟡 Warning
- **Anti-Pattern:** Speculative Generality / Technology-Enthusiast Architecture
- **Location:** `internal/platform/configs/decode.go:318-346`（配置解析）、`internal/boot/resources.go:77-103`（连接打开）、`internal/boot/container.go:96-118`（DI 提供）、`internal/platform/infrastructure/redis/redis.go`、`internal/platform/infrastructure/mongodb/mongodb.go`、`internal/platform/apperr/errors.go:161-171`（`WrapRedis`/`WrapKafka`/`WrapExternal`）
- **Confidence:** High
- **Evidence strength:** Observed（全量 grep：`infrastructure/redis|infrastructure/mongodb` 的非测试引用方仅 `boot/resources.go` 一处）
- **Failure or change scenario:** 使用者按注释相信「登录限流 across app instances」(`auth/usecase/types.go:52-54`)，实际限流由 MySQL 表实现（auth/adapters/mysql/store.go:160-201）——多实例部署时限流语义与文档承诺不符。每个新读者都要花时间确认 Redis/Mongo 是否真的在用；健康检查、配置面、启动路径都在为不存在的负载工作。
- **Primary principle:** YAGNI
- **Related principles:** KISS；文档与实现矛盾
- **Description:** 配置、资源生命周期、DI、健康检查四层都完整接线了 Redis 与 MongoDB，但没有任何模块的 store/usecase 消费它们。apperr 甚至预置了 `WrapKafka`——项目里不存在 Kafka。作为模板项目，「预留给未来业务选型」的解释与 AGENTS.md「禁止为未来不确定需求提前抽象」直接冲突。
- **Evidence:** grep 全仓库 `goredis`/`mongo` 仅出现在 boot 装配、infrastructure 自身包与各自测试；登录限流实际实现为 MySQL 表。
- **Measured/observed impact:** 阅读成本、误导性文档承诺、启动时多余连接尝试（配置了但连不上时表现为启动失败，让排障者误以为 Redis 是必要依赖）。
- **Recommendation:** 二选一，不要中间态：(a) 删除 Redis/Mongo 整条基础设施与 `WrapKafka`/`WrapRedis`，需要时再加回（模板项目首选，符合 AGENTS.md「优先清理坏设计」）；(b) 若定位是「多能力模板」，把登录限流真正改为 Redis 实现作为示范消费者，并修正注释。同时修正限流器注释与实现不符的问题。
- **Verification:** 删除后 `make verify` 全绿；grep 确认无残留引用；文档（README/configs/README.md）同步删除相应配置说明。

### Finding #3: settings usecase 聚合 4 个不相关配置域

- **Category:** Cohesion
- **Severity:** 🟡 Warning
- **Anti-Pattern:** God Object / Divergent Change
- **Location:** `internal/modules/settings/usecase/usecase.go`（1061 行，38 方法其中 29 导出）、`internal/modules/settings/usecase/types.go:12-37`（Store 接口 24 方法）、`usecase.go:1036-1061`（4 域错误混杂的映射表）
- **Confidence:** High
- **Evidence strength:** Observed
- **Failure or change scenario:** 修改字典导入逻辑、参数校验、版本打包格式中任何一处都要进入同一个 1061 行文件与同一个 Store 接口；四域的错误码、测试、review 范围互相牵连。新增第五个 `/system/*` 配置域时自然继续膨胀。
- **Primary principle:** SRP
- **Description:** 29 个导出方法覆盖 Configs（3 个）、Params（7 个）、Dictionaries（10 个）、Versions（9 个）四套互不关联的 CRUD + 各自的导入导出序列化。唯一聚合理由是路由同挂 `/system/*` 前缀（http/handler.go:42-71）。`Store` 接口因此膨胀到 24 方法，任何子域演化都要改这个巨型接口。
- **Evidence:** 方法清单按域分组后无任何跨域共享状态；四个子域各自持有独立的 domain 类型（settings/domain/system.go）。
- **Measured/observed impact:** 近 200 次提交中 settings/http/handler.go 变更 6 次；模块内 1061 行文件的变更合并冲突面与 review 成本随每域演化线性增长。
- **Recommendation:** 按 access 模块的先例（其 role/menu/api 三族因共享 roleScope 而聚合有理），settings 四域无共享内核，应拆为 config/param/dictionary/version 四个 usecase，各自定义小 Store 接口；handler 路由注册可保持 `/system/*` 前缀不变（路由前缀不是模块边界）。
- **Verification:** 现有 usecase_test.go（638 行）与 handler_test.go（540 行）按域拆分后行为断言全部保留通过。

### Finding #4: auth usecase 8 依赖、7 种职责，UpdateProfile 形成双写入口

- **Category:** Cohesion
- **Severity:** 🟡 Warning
- **Anti-Pattern:** God Object 趋势 / 职责错放
- **Location:** `internal/modules/auth/usecase/types.go:62-71`（8 字段）、`types.go:87`（7 位置参数构造函数）、`usecase.go:132-152`（UpdateProfile）、`usecase.go:401-441`（casbinSnapshot）、`usecase.go:497-522`（visibleMenus）、`internal/boot/business.go:359`（`accessStore` 填 3 个接口槽）
- **Confidence:** High
- **Evidence strength:** Observed
- **Failure or change scenario:** (a) `auth.UpdateProfile` 直接调 `u.admins.Update` 写 identity 存储，与 `identity.Usecase.Update`（identity/usecase/usecase.go:70，走 EnsureAssignableRoles 审计路径）形成同一聚合的双写入口——未来在 identity.Update 中加入的校验/审计天然被 auth 路径绕过。(b) casbin 快照构建 + 菜单树可见性计算是可独立的「授权快照服务」，与凭据认证、限流、session 生命周期混在一起。
- **Primary principle:** SRP
- **Related principles:** DIP（构造函数 7 个位置参数、同一 store 重复填槽，语义靠位置记忆）
- **Description:** Usecase 同时承担：凭据认证+bcrypt、登录限流、session 生命周期、当前用户资料更新（属 identity）、角色切换、RBAC casbin 引擎构建、菜单树可见性计算、路由授权、token 加密。
- **Evidence:** 见 Location 各行号；`identitySessionRevoker`（business.go:394-400）已存在反向桥接，说明 identity↔auth 的双向耦合已在 boot 显形。
- **Measured/observed impact:** auth/usecase/usecase.go 近 200 提交变更 7 次，是变更热点第二位；每次新增职责都要理解 8 个依赖的语义。
- **Recommendation:** 最小步骤：① 把 `UpdateProfile` 移交 identity（auth handler 经 usecase 接口调用 identity，或 handler 直接依赖 identity usecase）；② 提取 casbinSnapshot+visibleMenus 为 `authorizationSnapshot` 服务供 auth 与其他消费方共享；③ 构造函数改结构体参数消除 7 位置参数。
- **Verification:** auth usecase_test.go（579 行）行为断言不变；为 UpdateProfile 在 identity 侧补审计路径断言。

### Finding #5: RoleIsSuper 桥接把角色状态压成裸 bool，三处重复查询

- **Category:** Design
- **Severity:** 🟡 Warning
- **Anti-Pattern:** 裸 bool 投影（违反消费方接口语义规则）
- **Location:** 消费方接口 `internal/modules/apitoken/usecase/types.go:34-36`；桥接 `internal/boot/business.go:755-761`；三处调用 `internal/modules/apitoken/usecase/usecase.go:195-201`（issueTarget）、`220-227`（scopeListFilter）、`239-246`（ensureTokenVisible）
- **Confidence:** High
- **Evidence strength:** Observed
- **Failure or change scenario:** access 域已有「角色委托范围」概念（roleScope.assignableRoleIDs）；未来把委托范围引入 apitoken 可见性时，`(bool, error)` 接口必须破坏性修改，且三处独立 if 判断的授权语义要同步修改——这是把授权规则拆散到三个调用点的 Shotgun Surgery 预案。
- **Primary principle:** ISP（接口表达消费方真正需要的语义）
- **Description:** 桥接实现是 `role.IsSuperAdmin()` 的单 bool 投影。AGENTS.md 明文：「lookup interface 要表达消费方真正需要的语义，不要把重要状态压成裸 bool」。对照 access 自己的 `AdminRoleState{RoleIDs, ActiveRoleID}` 投影（access/usecase/types.go:41-44）保留了足够状态，这里压得过扁。另外三个调用点在单次 token 签发/列表流程中可能各自查一次 `FindRoleByID`。
- **Evidence:** 桥接函数体 7 行（business.go:755-761）；三个调用点均拿裸 bool 做独立授权分支。
- **Measured/observed impact:** 当前功能正确；扩展成本与重复查询是确定的结构性浪费。
- **Recommendation:** 把接口改成语义化投影，如 `RolePolicy.View(ctx, roleID) (RoleView, error)`，`RoleView` 携带 `IsSuper` 与（未来的）`AssignableRoleIDs`；一次查询结果在 usecase 内单次请求复用。
- **Verification:** apitoken usecase_test 现有 spy 扩展字段断言；新增「super 与非 super 两种 RoleView」的行为用例。

### Finding #6: recordOperation 逐字复制 5 份，Success:true 硬编码，失败操作永不入审计

- **Category:** Code（DRY）+ 审计完整性
- **Severity:** 🟡 Warning
- **Anti-Pattern:** Duplicated Code + 业务规则散落
- **Location:** `internal/modules/access/http/handler.go:376-394`、`identity/http/handler.go:180-198`、`apitoken/http/handler.go:130-148`、`settings/http/handler.go:624-642`、`fileasset/http/handler.go:352-370`（18 行函数体逐字相同）；配套 `OperationRecorder` 接口同样 5 份声明
- **Confidence:** High
- **Evidence strength:** Observed
- **Failure or change scenario:** 审计要求变更（例如记录失败操作、增加来源 IP、变更 message 格式）需要同步修改 5 处；更现实的缺陷是现在就存在的：`Success: true` 固定硬编码，usecase 返回错误时 handler 直接 `return err`，**失败的管理操作永远不会出现在审计日志中**——审计日志只能证明「谁做过什么」，无法证明「谁尝试做什么失败了」，这对 admin 系统的审计价值是实质缺口。
- **Primary principle:** DRY
- **Related principles:** 审计完整性（业务规则散落）
- **Description:** 五个模块的 handler 各自复制同一个 `recordOperation`（actorID 解析 → 构造 `auditusecase.OperationInput` 10 字段）。审计语义（何时记录、记录什么、成功失败）作为横切关注点没有任何单一事实来源。
- **Evidence:** grep 签名完全一致；函数体 diff 仅 struct 名不同。
- **Measured/observed impact:** 每新增一个带审计的模块就要再复制一份；失败操作审计缺口即刻存在。

## Appendix: Anti-Pattern Reference（本次检查涉及的）

- **God Object / Divergent Change**：单一模块因多个不相关原因反复变化（settings、auth）。
- **Speculative Generality / YAGNI**：为不存在的消费者保留的完整基础设施（Redis/Mongo/Kafka 错误包装）。
- **裸 bool 投影**：跨模块 lookup 接口丢失主体状态（RoleIsSuper）。
- **Duplicated Code**：跨模块逐字复制（recordOperation ×5、分页 ×6、错误表 ×7 等）。
- **Missing Transaction Boundary**：多步写操作无原子性（导入路径）。
- **Full-table Load + In-memory Pagination**：与 SQL 下推并存的不一致持久化模式。
- **Repeated Linear Scan**：循环内线性查找缺 map 索引（冷路径合集）。
- **Test Blind Spot**：整层（mysql adapter）零覆盖 + 调用计数式断言（audit）。
- **Presentation in Domain**：下载序列化/文件名规则下沉 usecase（settings JSON 导出）。
- **已检查且无问题的**：Big Ball of Mud、循环依赖、层次穿透（domain→transport/DB）、SQL 注入、深嵌套、goroutine 泄漏、资源未关闭、循环内排序、Manager/Helper/Util 命名、全局状态、服务定位器。
